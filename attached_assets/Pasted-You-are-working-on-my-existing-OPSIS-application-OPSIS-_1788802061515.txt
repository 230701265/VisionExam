OPSIS is an accessibility-first examination platform designed especially for blind and visually impaired users. The existing application uses React on the frontend, Express on the backend, and Drizzle/PostgreSQL for persistence.

I want you to ADD a complete voice accessibility layer to the EXISTING OPSIS application.

IMPORTANT:

* Do NOT rebuild the application from scratch.
* Do NOT remove or break existing functionality.
* Inspect the existing project structure, routes, components, hooks, database schema, keyboard shortcuts, examination UI, editor, timer, results system, and accessibility implementation before making changes.
* Reuse existing functions wherever possible.
* Voice commands must trigger the same application functions used by keyboard/buttons.
* Keyboard and screen-reader accessibility must remain fully functional even if voice is unavailable.
* Do not make voice the only way to perform any action.

3. COMMAND BUS
==============

Create a centralized command bus.

Example conceptual structure:

type CommandId =
| 'nextQuestion'
| 'previousQuestion'
| 'readQuestion'
| 'readOption'
| 'selectOption'
| 'readTimer'
| 'runTests'
| 'readResults'
| 'help'
| 'repeat'
| 'cancel'
| 'increaseSpeechRate'
| 'decreaseSpeechRate'
| 'pauseSpeech'
| 'resumeSpeech'
| 'stageSubmit'
| 'confirmSubmit';

Create a CommandDef structure containing:

* id
* phrases
* scope
* destructive
* handler
* optional argument parser

Example:

{
id: "nextQuestion",
phrases: [
"next question",
"next",
"go to next question",
"skip ahead"
],
scope: "question",
destructive: false,
handler: () => existingNextQuestionFunction()
}

The Command Bus must be the single execution layer for:

* keyboard commands
* button actions where practical
* voice commands

This is extremely important.

Voice should NOT become a separate parallel implementation of the application.

4. SPEECH RECOGNITION
=====================

Implement browser SpeechRecognition first.

Support:

window.SpeechRecognition

and:

window.webkitSpeechRecognition

Create a provider abstraction such as:

STTEngine

with methods conceptually equivalent to:

start()
stop()
onPartial
onFinal
onError

This allows a future provider such as Deepgram to be added without rewriting the command system.

Detect unsupported browsers gracefully.

If SpeechRecognition is unavailable:

* show an accessible message
* keep all keyboard functionality working
* do not crash
* do not repeatedly request microphone permission

Recognition should primarily be used for SHORT COMMANDS.

Do NOT implement code dictation.

Voice should control the examination interface, not replace keyboard/braille for writing source code.

==================================================
5. PUSH-TO-TALK
===============

The default voice mode must be PUSH-TO-TALK.

Use:

Ctrl + Shift + Space

as the default global hotkey.

When activated:

1. Start speech recognition.
2. Play a short listening earcon.
3. Announce/accessibly expose:
   "Listening."
4. Listen for approximately 4 seconds.
5. Stop recognition automatically.
6. Play a closing earcon.
7. Process the final transcript.

Do NOT continuously record microphone audio by default.

This is especially important during examinations because continuous listening creates privacy and examination-integrity concerns.

Make the hotkey configurable if the existing accessibility/settings architecture supports it.

==================================================
6. VOICE MODES
==============

Add an accessibility setting:

voiceMode

* off
* push-to-talk
* wake-word

Wake-word should be architected as a future option but should NOT be falsely presented as implemented unless it actually works.

If an admin/exam configuration system exists, add an exam-level voice mode:

This allows an administrator to disable voice for specific exams.

7. COMMAND MATCHING
===================

Voice command recognition must be deterministic.

Normalize transcripts by:

* converting to lowercase
* removing unnecessary punctuation
* trimming whitespace
* normalizing common speech variations

Use explicit phrase/synonym matching.

Examples:

"next question"
"next"
"go to next question"

→ nextQuestion

"previous question"
"go back"
"previous"

→ previousQuestion

"read question"
"read this question"
"what is the question"

→ readQuestion

"read option A"
"read answer A"

→ readOption("A")

"choose A"
"select A"
"answer A"

→ selectOption("A")

"read timer"
"time remaining"
"how much time is left"

→ readTimer

"run tests"
"run the tests"
"execute tests"

→ runTests

"read results"
"show my results"
"tell me my result"

→ readResults

"help"
"what can I say"
"voice commands"

→ help

"repeat"
"say that again"

→ repeat

==================================================
8. CONFIDENCE SAFETY GATE
=========================

Every recognized voice command must have a confidence value where available.

Use a default confidence threshold around:

0.75

If confidence is below the threshold:

DO NOT execute the command.

Instead:

1. Store the transcript temporarily.
2. Speak:
   "I heard: [transcript]. Please repeat."
3. Keep the interface in a safe state.

Never silently execute a potentially incorrect command during an examination.

Do not use fuzzy matching or an LLM to guess destructive commands.

"cancel"
